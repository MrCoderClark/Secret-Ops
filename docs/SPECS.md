# SecretOps — Build Specification

This file translates the design docs (`README.md`, `ARCHITECTURE.md`,
`SECURITY.md`, `CLI.md`, `schema.prisma`) and the dashboard mock
(`mock-ui-design.png`) into an ordered, testable build spec. Scope boundaries
and acceptance criteria below are binding; anything not listed is out of scope
for the first cut.

---

## 1. Product scope

SecretOps is a self-hosted control plane for application secrets. One
organization, many projects, each project has `dev / staging / prod`
environments, each environment holds secrets and feeds one or more sync targets
(local, CI/CD, Kubernetes, Terraform, serverless, VM).

### In scope (v1)

- Dashboard with the nine pages the README lists
- REST API covering everything the dashboard does, plus a pull-bundle route
- Envelope encryption with per-version DEKs wrapped by a KEK
- Hash-chained audit with a verifier
- RBAC (5 roles) with per-environment grants and JIT access requests
- Rotation (auto + manual modes) run by a worker
- Drift detection run by a worker
- Scoped machine tokens for CI/CD and pull agents
- Policy engine evaluated on write
- Docker + docker-compose deployment
- Seeded demo data so the app is explorable after `npm run dev`

### Out of scope (v1, documented as "known gaps")

- Real sync-provider adapters (stub only — plan/apply/observe contract complete,
  bodies are no-ops that prove the value decrypts)
- SSO / OIDC / SAML
- MFA verification at login (field exists, policy exists, no enforcement)
- Pull-bundle signature
- Crypto-shredding / hard delete
- Multi-instance rate limiting (in-process only)
- Migration directory (generated on first `prisma migrate dev`)

## 2. Stack

| Layer | Choice | Notes |
|---|---|---|
| Runtime | Node.js ≥ 20 | ESM, `tsx` for scripts |
| Framework | Next.js 14 (App Router) | Standalone output for Docker |
| UI | React 18 + Tailwind 3 | Server components by default |
| DB | PostgreSQL 16 | Via Prisma 5 |
| Validation | Zod 3 | All write paths |
| Auth | HS256 JWT in `sop_session` cookie | `jose`; argon2id for passwords |
| Crypto | Node `crypto` | AES-256-GCM everywhere |
| Build | `prisma generate && next build` | No live DB at build time |

Pinned versions already live in `package.json`. Do not add dependencies without
a reason that cannot be met by the standard library.

## 4. Data model

The Prisma schema is already written and is the source of truth. Do not drift
from it without updating `ARCHITECTURE.md` and `SECURITY.md` in the same change.

Invariants the code must preserve:

1. `SecretVersion` is append-only. No update path exists. The next version
   number is `max(version) + 1` per `secretId`.
2. A write that produces the same `valueHash` as the current version is a
   no-op — do not insert a new row.
3. `SyncState` is upserted on `(syncTargetId, secretId)` after every observe.
4. `AccessEvent` rows are written inside a transaction that reads the tail
   `(organizationId, seq)` and writes `(seq + 1, prevHash = tail.hash)`.
   `(organizationId, seq)` is unique, so a race loses and must retry.
5. Soft delete sets `deletedAt`; list queries filter it out.

## 5. Crypto

`web/lib/crypto.ts` exports:

```ts
type Keyring = {
  activeKeyId: string;
  keys: Map<string, Buffer>; // 32 bytes each
};

function resolveRootKey(): Keyring;              // from SECRETOPS_ROOT_KEYS
function seal(plaintext: string, kr: Keyring): SealedValue;
function open(sv: SealedValue, kr: Keyring): string;
function rewrapVersion(row: SecretVersionRow, kr: Keyring): Partial<SecretVersionRow>;
function hashValue(plaintext: string): { hash: string; fingerprint: string };
function generate(spec: string): string;          // "base64:32" | "hex:32" | "uuid" | "alnum:64"
function hashPassword(pw: string): Promise<string>;
function verifyPassword(hash: string, pw: string): Promise<boolean>;
```

Rules:

- GCM nonce is 12 random bytes per encryption. Never reused.
- `keyId` on every version. On read, if the active key differs, compute a
  rewrap and return it so the caller can persist it.
- In production (`NODE_ENV=production`), `resolveRootKey()` throws if
  `SECRETOPS_ROOT_KEYS` is empty. In development, derive a deterministic
  throwaway key and log a warning once per process.
- The KEK never leaves the process. Do not include it in any log line, error
  message, response body or exception stack.

## 6. RBAC and scoping

`web/lib/rbac.ts` is the single source of truth.

```ts
type Actor =
  | { kind: "user"; id: string; email: string; role: Role; orgId: string; grants: Grant[] }
  | { kind: "machine"; id: string; principal: string; scopes: string[]; envIds: string[] | null; orgId: string };

function can(actor: Actor, capability: Capability): boolean;
function canReadValue(actor: Actor, env: Environment): boolean;
function canWriteValue(actor: Actor, env: Environment): boolean;
```

The capability matrix is the table in `SECURITY.md`. Protected environments
(`stage ≥ 2 || protected`) require an Admin+ role OR an unexpired grant
scoped to that environment or secret.

Both the UI and the API call these helpers. Hiding a button in the UI is not
enforcement — the server check is.

## 7. API contracts

See `README.md` and `CLI.md` for the full surface. For every route:

- Parse the body with the Zod schema in `web/lib/validation.ts`.
- Resolve the actor with `resolveActor()` from `web/lib/session.ts`.
- Call the capability helper. Return `403` on denial AND record a DENIED event.
- Delegate to the service layer. Routes contain no business logic.
- Return JSON with `Cache-Control: no-store` on anything carrying secret
  material (`/reveal`, `/bundle`).

### Error shape

```json
{ "error": "human sentence", "code": "optional_machine_code", "fieldErrors": { "field": ["message"] } }
```

Statuses match the `CLI.md` error table verbatim.

## 8. UI

The mock (`mock-ui-design.png`) sets the look: dark theme, left sidebar with
labelled nav, header with a wide search input and a `Healthy` pill, a page
title row with `+ New secret` and `Run sync` actions, and four metric cards
across the top.

### Shell

- Sidebar: `SecretOps` wordmark + lock glyph, the org name as a small
  all-caps label, the nine nav items in the order shown, user card at the
  bottom with avatar, name, role, and a `Sign out` button.
- Header: full-width search input (opens the command palette on focus or
  <kbd>⌘K</kbd>), status pill on the right (`Healthy` when `/api/health` is
  green, `Degraded` otherwise).
- Command palette: searches across secrets, paths, actors (`/api/search`).

### Overview

Mirror the mock exactly:
- Four metric cards — Secrets Under Management / Drift Detected / Rotation
  Overdue / Audit Chain (`Verified` or `Broken at seq N`).
- Sync posture table — target name + kind badge, environment, status pill,
  coverage bar, last run (relative time).
- Rotation runway — ordered by days-left ascending, cap at five.
- Recent activity — last ten events, relative time, actor avatar.

### Secrets / Sync / Audit

All three are filterable tables. Revealing a value is a client component that
POSTs to `/api/secrets/:id/reveal`, holds the plaintext in state only, and
auto-clears after 30 seconds. A countdown ring on the cell is sufficient.

### Theming

Tailwind with CSS variables for surface, border, text, muted, accent. Default
dark, respect `prefers-color-scheme`. All colour tokens live in
`globals.css` — components reference them, never raw hex.

## 9. Worker

`scripts/worker.ts` runs two loops:

- Rotation sweep — every `ROTATION_SWEEP_MS` (default 6h). For each secret with
  a policy where `now - lastRotated > intervalDays`: `auto` calls
  `rotateSecret()`, `manual` writes a `RotationEvent{status:"SCHEDULED"}`
  and an audit event.
- Drift sweep — every `DRIFT_SWEEP_MS` (default 30m). For each enabled target,
  call `planSync({ observeOnly: true })` and upsert `SyncState`.

The worker uses the same Prisma client and crypto layer. It must not reach into
HTTP handlers.

## 10. Seed

`prisma/seed.ts` creates the `Acme Corporation` org with:

- Four users matching the README table, shared password `demo-password-change-me`
- Three projects (Payments API, Customer Portal, Data Platform)
- Nine environments (`dev / staging / prod` × three projects)
- ~39 secrets across them with realistic names (`DATABASE_URL`, `STRIPE_SECRET_KEY`,
  `OIDC_CLIENT_SECRET`, `KAFKA_SASL_PASSWORD`, `SESSION_SECRET`, …)
- Nine sync targets matching the mock rows and the kinds enum
- Two rotation policies, assigned to the keys the mock shows in runway
- Two seeded `AccessRequest` rows — one PENDING, one APPROVED
- One pre-written `Policy` of each kind
- Enough `AccessEvent` rows (generated via `recordEvent`, so the chain is
  valid) to populate the audit page with realistic history

The seed prints the credentials it created at the end so the user can sign in.

## 11. Acceptance criteria

The build is done when all of these pass from a clean checkout:

1. `npm install && npx tsx scripts/bootstrap.ts` produces a usable `.env`.
2. `docker compose up -d postgres && npx prisma migrate dev && npx prisma db seed`
   completes without error.
3. `npm run dev` serves the dashboard at `localhost:3000`.
4. `npm run typecheck` and `npm run build` both pass.
5. Signing in as each of the four seeded users shows the capabilities the
   SECURITY matrix promises — verified with the "testing changes by hand"
   steps in `CONTRIBUTING.md`.
6. `docker compose up -d` builds and starts the full stack; the health check
   reports ready within 30s.
7. The chain verifier reports `Verified` on seed data, and detects a tamper
   when a row is edited directly in Postgres.
8. The CLI examples in `CLI.md` succeed against a running instance.

Anything in `README.md § Known gaps` is explicitly accepted and does not block
the milestone.
